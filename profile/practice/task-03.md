# Задание 3 — Старт своего проекта: экраны, навигация и архитектура


---

## Цель

Перенести согласованные требования и макеты своего проекта в первый работающий Android-каркас:
2–3 экрана, один сквозной сценарий, навигация, состояние и DI.

Тема проекта берётся из `projectTheme.md`, согласованного в Задании 2. Если тема ещё не
согласована — сначала согласуйте её с преподавателем; работа без согласованной темы не
принимается.

---

## 1. Общее описание

Нужно разработать Android-приложение на Kotlin + Jetpack Compose, в котором уже виден **один
полный пользовательский сценарий вашего проекта**: от стартового экрана через основное действие
до результата.

Приложение работает **полностью локально** на демонстрационных данных. Сеть, база данных и
внешние сервисы в этом задании не используются.

Работа состоит из двух частей:

- **Часть А (8 баллов)** — работающее приложение: экраны, навигация, состояние, DI, данные,
  обработка пустых и ошибочных ситуаций.
- **Часть Б (2 балла)** — документация: README, карта маршрутов и архитектуры, обновлённые
  макеты и трассировка требований.

---

## 2. Общие требования к реализации

1. Приложение — Android-проект на **Kotlin + Jetpack Compose + Material 3**.
2. Проект собирается командой `./gradlew :app:assembleDebug` и запускается на эмуляторе или
   устройстве без ручных правок.
3. Навигация между экранами — **Navigation Compose (`NavHost`)**. 
4. Состояние экранов хранится в **ViewModel** и переживает поворот экрана. Для состояния
   используется `StateFlow` (предпочтительно) или `mutableStateOf`; чтение — через
   `collectAsStateWithLifecycle()` / `collectAsState()`.
5. Зависимости предоставляются через **Hilt**: `@HiltAndroidApp`, `@AndroidEntryPoint`,
   `@HiltViewModel`, модули и `@Inject`. Создание репозиториев и ViewModel вручную в
   composable-функциях не допускается.
6. Данные — **локальные демонстрационные**: список в коде, JSON в `assets` или локальный файл.
   Room, DataStore, Retrofit, OkHttp и любые сетевые запросы в этом задании запрещены.
7. Бизнес-логика (проверки, расчёты, фильтрация, смена статусов) живёт в обычных Kotlin-классах
   и функциях без импортов Android и Compose.

## 3. Функциональные требования

### 3.1. Экраны

В приложении должно быть **не меньше трёх экранов**:

1. **Стартовый экран** — точка входа в основной сценарий: список сущностей, меню или форма.
2. **Экран действия** — работа с одной сущностью или выполнение основного действия: детали,
   редактирование, прохождение, расчёт.
3. **Экран результата** — итог, подтверждение или сводка; из него есть возврат на стартовый
   экран или повтор действия.

Экраны должны соответствовать макетам из Задания 2. 

Если объективно ваш сценарий не требует трёх экранов (например, приложение из одного экрана),
третий экран можно заменить осмысленным (настройки, история, справка) 

### 3.2. Сквозной сценарий

- Пользователь проходит путь **стартовый экран → действие → результат** без тупиков и
  «болтающихся» экранов.
- Между экранами передаётся **аргумент навигации** (идентификатор, имя, режим), а не глобальная
  переменная или синглтон.
- Системная кнопка «назад» работает осмысленно: с результата возвращает на предыдущий шаг, не
  создаёт дубликатов экранов и не выбрасывает из приложения в неожиданный момент.
- Состояние экрана действия (введённый текст, выбранный элемент, прогресс) **сохраняется при
  повороте**.
- Если данных нет — показывается понятная надпись и способ вернуться/добавить данные, а не
  пустой экран.
- Некорректный ввод не приводит к падению: показывается сообщение, действие блокируется или
  не выполняется.

### 3.3. Данные

- Демонстрационный набор должен позволять пройти сценарий целиком. Для списка — не меньше
  трёх–пяти сущностей.
- Источник данных спрятан за интерфейсом (например, `XxxRepository`); реализация —
  in-memory, JSON в `assets` или локальный файл.
- Замена источника данных не должна требовать изменений в UI.
- Должно быть достижимо **пустое состояние** (например, отдельный режим или очистка демо-данных).

### 3.4. Бизнес-логика

- В приложении есть минимум одно **бизнес-правило**: проверка ввода, расчёт, фильтрация,
  сортировка, смена статуса и т.п.
- Правило находится в domain-классе или функции и может быть вызвано без эмулятора и без UI.
- UI не считает бизнес-результат сам: он получает готовое состояние из ViewModel.

---

## 4. Архитектура

Архитектура проверяется на защите. Ожидается разделение на слои:

- **UI** — composable-функции и ViewModel;
- **domain** — модели и бизнес-правила;
- **data** — репозиторий и источник демо-данных.

Требования:

- UI-экран получает состояние и колбэки, не хранит бизнес-состояние и не создаёт зависимости.
- ViewModel отдаёт `UiState` (data class, sealed interface или эквивалент) и принимает события.
- Зависимости ViewModel и репозитория предоставляются Hilt.
- Один экран — один ViewModel или один ViewModel на сценарий; выбор объясните в документации.
- Никаких `GlobalScope`, блокирующих операций в main-потоке и глобальных синглтонов вместо DI.

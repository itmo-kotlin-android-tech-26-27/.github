Покрыть юнит-тестами бизнес-логику и ViewModel своего проекта: проверить правила, состояния

## Часть А. Тесты (8 баллов)

### 1. Запуск

- тесты лежат в `app/src/test/java/...`;
- `./gradlew test` завершается успешно;
- в отчёте видно не меньше **8** тестов;
- тесты не обращаются к сети и не используют настоящую Room-базу;
- JUnit 4 или JUnit 5 — как в шаблоне курса; главное, чтобы тесты запускались через
  `./gradlew test`, а не требовали эмулятора.

### 2. Тесты домена (3–4 теста)

Проверяется бизнес-правило из Задания 3:

- корректный ввод → ожидаемый результат;
- некорректный ввод → ошибка/отказ;
- граничные значения (пустая строка, ноль, максимум, отрицательное число — что применимо);
- как минимум один тест на «неочевидный» случай.

Доменные тесты не должны требовать Android-контекста.

### 3. Тесты ViewModel (3–4 теста)

- начальное состояние;
- переход `Loading → Success`;
- переход `Loading → Error` при ошибке репозитория;
- пустой ответ → `Empty` (если такое состояние есть);
- повторный запрос после ошибки снова приводит к `Success`.

Репозиторий подменяется **фейком** (ручная реализация интерфейса) или MockK — на выбор.
Фейк предпочтительнее: он проще и не требует мок-фреймворка.

### 4. Тесты Flow

- минимум один тест проверяет последовательность значений `Flow`/`StateFlow`;
- используется `Turbine` (`test { ... awaitItem() }`) или `kotlinx-coroutines-test`;
- тест не «спит» реальные секунды: время управляется `TestDispatcher`.

Базовый каркас:

```kotlin
@OptIn(ExperimentalCoroutinesApi::class)
class QuizViewModelTest {
    private val dispatcher = StandardTestDispatcher()

    @Before fun setUp() = Dispatchers.setMain(dispatcher)
    @After fun tearDown() = Dispatchers.resetMain()

    @Test
    fun `success state after load`() = runTest {
        val vm = QuizViewModel(FakeRepository(items = listOf(item)))
        vm.load()
        advanceUntilIdle()
        assertEquals(UiState.Success(listOf(item)), vm.state.value)
    }
}
```

Имена тестов — на русском или понятном английском. Структура — arrange / act / assert.

### 5. Что не тестируем

- Compose UI и навигацию (это instrumentation-тесты, отдельная история);
- настоящий Retrofit и настоящий сервер;
- Room на устройстве;
- покрытие 100% — не требуется.
